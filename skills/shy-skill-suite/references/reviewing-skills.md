# 技能复审 · 操作手册

> 本文件规定 **AI 生成 / 改写技能后如何复审该技能**，以及如何提出真正提升效果的改进意见。
> 适用对象：任一技能的完整文件集（`SKILL.md` / `scripts/` / `references/` / `assets/`）。
> 面向读者：执行复审的人或 AI。依据见 §5。

---

## 1. 复审只回答两个问题

技能存在的唯一理由是**改变 agent 的行为**。复审不是"逐条检查文件"，而是对两问给出有证据的判断：

1. **触发**：该触发时触发、不该触发时不触发吗？
2. **有效性**：触发后，它是否真的改变了 agent 的行为，且改对了？

**每个检查项都必须能落到这两问之一。** 复审的第一产物是**证据**（真实执行轨迹），不是意见清单。

**预算视角**：技能内容花两种预算——`description` 常驻上下文，`SKILL.md` 正文激活后占用上下文。复审默认假设"内容偏多"，优先找**不买行为改变的内容**：no-op、cache、duplication、sprawl、sediment（各自定义见 Step 2、Step 3）。**优先删，其次改，最后才加。**

---

## 2. 复审流程

按顺序执行；前一步没有证据支撑时，后一步的结论不可靠。每步末尾的**完成判据**是本步收工的界限。

### Step 0 · 立靶（跳过这步，后面全是空谈）

- 读对应需求文档 `docs/<skill>/requirements/REQ-NNNN-*.md`，明确"本技能要改变什么行为"，作为复审基准；无需求文档则先补一份，或把讨论结论记下作基准。
- 记录技能文件集与常驻的 `description`。

**完成判据**：手里有 1 份"要改变什么行为"的基准，且技能文件集与 `description` 已列出。

### Step 1 · 触发审查（最高价值：触发错了，技能等于不存在）

`description` 是唯一的触发指针，它措辞的精度决定技能何时被想起。

- **该触发的触发了吗**：覆盖真实用户会说的说法——口语、错别字、缩写，以及**不点名域名的说法**（用户说的是需求，不是技能名）。
- **不该触发的没触发吗**：重点看 **near-miss**（共享关键词但任务不同），这才是过宽的信号；"问天气"这类无关查询测不出任何东西。
- **措辞**：用祈使句（"当……时使用本技能"）、聚焦**用户意图**而非实现机制、对边界场景宁可"pushy"地列全。
- **硬约束**：`description` ≤ 1024 字符；`name` 与技能目录同名，仅小写字母 / 数字 / 连字符。
- **调用方式选对了吗**：只有人手动调用、且没有别的技能要引用它 → 应设为 user-invoked（不付常驻上下文）；否则才 model-invoked。选错是持续的上下文浪费。
- **与相邻技能的边界**：是否有职责重叠、互相抢触发。

**怎么验**：构造 8–10 条 should-trigger 与 8–10 条 should-not-trigger（含 near-miss）查询，各跑多次算**触发率**；把查询分成 train/validation 两半，只用 train 的失败去改措辞，用 validation 判断是否泛化——防止把描述过拟合到测试句子上。

**完成判据**：正例与负例的触发率都过阈值（默认 0.5），且描述符合硬约束。

### Step 2 · 有效性审查（技能是否真的改变了行为）

**先做整技能对照**：取 2–3 个真实 prompt，各跑**有技能 / 无技能**两遍（改进已有技能时，用旧版快照作基线），比较通过率与 token / 耗时。没有 delta 就不能说技能"有效"，最多说它"没坏"。

然后对每条指令追问：**"没有这句，agent 会做错吗？"** 不会 → 它是 no-op 或 cache，删。

- **真实专长（AI 生成技能的头号风险）**：技能里有多少内容是**这个项目 / 领域独有、且模型推不出来**的？若整篇换成任何同类项目仍成立，就是通用废话（"handle errors appropriately"），必须回填真实材料——真实任务步骤、runbook、事故与修复、代码评审意见、diff。
- **no-op**：模型默认就会做的（"要注意边界""保持简洁"）。判断标准是模型默认行为，不是个人偏好；不确定就删掉这句跑一次对比。
- **cache**：把环境本身能查到的东西抄进技能（`package.json` 脚本、`--help` 输出、目录结构）。环境是事实源，抄写会过期；只保留**查不到的东西**：不成文的约定、选择背后的原因、配置不承认的坑。
- **gotcha 是否缺失**：最值钱的内容是**反直觉的项目事实**（软删除要加 `WHERE deleted_at IS NULL`、同一 ID 三个服务三个叫法）。轨迹里 agent 犯过的错、你纠正过的地方，回填成 gotcha——这是最直接的迭代改进。
- **粒度是否内聚**：技能是否覆盖一个内聚工作单元（一件事的完整闭环）？太窄会为一次任务加载多个技能，太宽则触发不准。
- **控制力度是否匹配脆弱度**：顺序敏感、必须一致的 → 写死（"按此序列执行，勿加 flag"）；多解、容错 → 解释**为什么**，让 agent 自己判断。多数技能是混合的，逐段校准。
- **给默认而非菜单**：多个方案并列会让 agent 反复试错；挑一个默认，其余一句带过。
- **教方法而非给答案**：可复用的 procedure 优于只对当前实例有效的具体答案（输出模板、格式约束这类"具体"是合理的例外）。
- **事实准确性**：版本号、API 名、参数、外部链接是否过期或写错——过时事实比缺失更有害。

**完成判据**：整技能对照有 delta 证据；每条指令都过了"没有它会做错吗"，且能指出它防住的具体错误。

### Step 3 · 结构与预算审查（信息层级）

- **`SKILL.md` 是否超预算**：目标 < 500 行 / < 5k token。超出部分下放到 `references/`，并在主文件给出**何时加载**的指针（"API 返回非 200 时读 `references/api-errors.md`"），而不是笼统的"详见 references/"。
- **分支是否按需披露**：只有部分分支需要的内容，移到主文件之外——分支是最干净的披露判据。
- **co-location**：一个概念的定义、规则、例外是否聚在同一标题下，而不是散落多处。
- **单一事实源**：同一含义是否在多处重复（重复会同时增加维护成本和该含义在注意力里的权重）。
- **sprawl / sediment**：是否只是太长、是否有早已失效的陈旧层；逐段问"这行还相关吗"。
- **引用层级**：文件引用是否相对技能根、保持一层深，避免嵌套引用链。
- **可收敛的散句**：反复出现的三词短语、用一句话去指代一个概念的段落，能否收敛成一个 **leading word**（模型已认识、能反复用单 token 唤起的词）。
- **禁止句**：以"不要做 X"表达的指令会把 X 拉进上下文、反而更可得；能改成正面目标就改（"写一行注释"而非"不要写多行注释"）。

**完成判据**：`SKILL.md` 在预算内；每条下放内容都有触发它的指针；无 duplication / sprawl / sediment。

### Step 4 · 步骤与完成判据审查

- **每一步有可判定的完成判据吗**：agent 能分清"做完"和"没做完"吗？模糊的边界（"理解到位"）会诱发**提前收工**。
- **判据的强度够吗**："每个改动的模型都要交代"逼出彻底工作，"产出一份变更清单"不能。
- **是否被后续步骤诱惑**：后续步骤可见时 agent 会急着结束当前步；若观察到抢跑，优先**收紧判据**，仍不行再拆分序列（拆分只在真正的上下文边界——交接或子 agent——才有效）。
- **破坏性 / 批量操作**：是否有 plan → validate → execute 的结构（先产出中间计划，用事实源校验，再执行）？是否支持 `--dry-run` / 显式确认？是否有验证回路（做 → 校验 → 修 → 再校验，通过才继续）？

**完成判据**：每个 step 都能指出其完成判据，且判据可判定。

### Step 5 · 脚本与资源审查

- **非交互**：脚本从参数 / 环境变量 / stdin 接收全部输入（等待 TTY 会挂死）；缺参时给出带用法的清晰报错。
- **`--help` 完整**：简述 + 参数 + 示例 + 退出码含义——这是 agent 了解接口的主要途径。
- **错误可行动**：说清"哪里错、期望什么、下一步试什么"，而不是 `invalid input`。
- **输出结构化**：优先 JSON/CSV；**数据走 stdout、诊断走 stderr**，便于管道消费。
- **幂等**：agent 会重试，"不存在则创建"优于"重复即失败"。
- **安全默认与输出规模**：破坏性操作要 `--confirm`/`--force`；大输出默认摘要并提供 `--offset`/`--output`，避免被工具层截断丢失关键信息。
- **依赖与版本**：脚本是否自包含或明确声明依赖、是否需要固定版本；技能是否需要 `compatibility` 声明运行前提。
- **该固化的逻辑**：轨迹里 agent 每次都在重造同一段逻辑（画图、解析、校验）→ 写成脚本放进 `scripts/`，一次测试、反复复用。

**完成判据**：脚本逐项过了本步清单——非交互、`--help`、结构化输出、幂等、输出规模可控。

### Step 6 · 安全、边界与自包含审查

- **来源与网络**：是否有可疑的外部网络访问、数据外泄指令、未声明的依赖或捆绑资源；安装来源是否可信。
- **凭据**：技能文件里不得出现密钥、token、个人路径等敏感信息。
- **破坏性护栏**：改用户内容前是否备份 / 可回退 / 先确认。
- **能力降级**：平台差异、缺失能力、降级路径是否写明（如某格式不支持某语法时的替代写法）。
- **自包含**：技能文件只引用技能自身（相对技能根），不引用仓库级 `docs/` 等外部路径——技能会被单独复制部署，外部引用就是悬空指针。

**完成判据**：来源、凭据、破坏性护栏、能力降级逐项过；自包含检查无悬空引用。

### Step 7 · 汇总裁决

把发现归入三档，并给出结论：

| 结论 | 条件 |
| --- | --- |
| **可合入** | 无 P0，触发与有效性证据通过 |
| **改后可合入** | 存在可定位、可修复的问题 |
| **需重做** | 触发或核心行为错误，或安全问题 |

**报告格式**（每条一行，不复述技能内容）：

```
[优先级] 位置(file:line) — 问题（附证据）→ 影响（触发/有效性/结构/安全）→ 建议改动 → 预期行为变化
```

优先级：`P0` 阻断（触发错误 / 行为错误 / 安全）→ `P1` 行为提升 → `P2` 精简与可读性。

**完成判据**：给出三档结论之一，并附一份带优先级的改进清单。

## 3. 如何提出改进意见（让意见真的有用）

- **先删后加**：提新增前先问"这是不是已有内容的重复或补丁"。
- **泛化，别打补丁**：修的是底层类别，不是测试集里的那句特例。把失败查询的**关键词**抄进 `description` 就是过拟合——要找它代表的类别。
- **带证据**：每条意见附轨迹片段或具体来源；没跑过、没证据的判断只能标"待验证"，不能当结论。
- **给 why**：解释性指令（"做 X，因为 Y 会导致 Z"）比硬规则更可靠。
- **可落地**：说清改哪里、改成什么、预期行为怎么变；只给"这里可以更好"不是意见。
- **只提影响一致性或可读性的措辞意见**：纯偏好不值得占一行。
- **过约束就做减法**：加规则后通过率不升反降，说明约束过头，应删规则再测。

---

## 4. 复审自身的反模式

- **静态打勾不跑**：不看真实轨迹的复审，必然漏掉真正的失效（绕路、误触发、抢跑）。
- **只审 `SKILL.md`**：不看 `scripts/`、`references/`，也不看真实触发，等于只审了技能的三分之一。
