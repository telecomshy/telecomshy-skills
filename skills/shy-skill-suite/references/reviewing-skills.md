# 技能复审 · 操作手册

> 本文件规定 **AI 生成 / 改写技能后如何复审该技能**，以及如何提出真正提升效果的改进意见。
> 适用对象：任一技能的完整文件集（`SKILL.md` / `scripts/` / `references/` / `assets/` / `commands/` / `evals/`）。
> 面向读者：执行复审的人或 AI。依据见 §5。

---

## 1. 复审回答三个问题

技能存在的唯一理由是**改变 agent 的行为**。复审不是"逐条检查文件"，而是对三问给出有证据的判断：

1. **触发**：该触发时触发、不该触发时不触发吗？
2. **有效性**：触发后，它是否真的改变了 agent 的行为？
3. **需求一致性**：它做的，正是需求要求的吗（没漏、没多、没做错）？

三问映射到**三条轴**：触发与有效性归**行为**轴，需求一致性归**需求（Spec）**轴；**标准**轴（结构 / 脚本 / 安全）另立、不对应上述三问之一。**报告时分开、不合并**：一条轴过、另一条轴败是常事，合并会互相掩盖。

**每个检查项都必须能落到这三问之一。** 复审的第一产物是**证据**（真实执行轨迹），不是意见清单。

**预算视角**：技能内容花两种预算——`description` 常驻上下文，`SKILL.md` 正文激活后占用上下文。复审默认假设"内容偏多"，优先找**不买行为改变的内容**：no-op、cache、sediment、重复（违反单一事实源）——定义见 `writing-skills.md` §7。**优先删，其次改，最后才加。**

---

## 2. 复审流程

按顺序执行；前一步没有证据支撑时，后一步的结论不可靠。每步末尾的**完成判据**是本步收工的界限。

### 成本闸门 · 按需多跑（委派任何子代理之前）

复审要派子代理（executor / grader / spec-reviewer / analyzer / comparator）。**开始前一次性问清三件事**（别分几次打扰）：

1. **价值与范围**：多跑能提升质量，但**只针对「剪枝（Step 4）+ 有效性内容发现（Step 2）」**；触发、安全两类**单跑**（触发已有 `evals` 与机械核查，多跑产出的多为噪声）；Spec 轴（Step 3）走 `run_checks.py`，不涉及。
2. **跑几轮**：**建议 3 轮**；可选 单轮 / 2 / 3。**用户不明确回答 → 单轮**（保守，不擅自烧 token）。
3. **子代理模型**：**默认＝主代理的模型**；用户可报模型 ID 覆盖（可查 `opencode.models`）。多跑时若给了多个模型，逐跑轮换；否则同模型多跑。

- **免问例外**：用户本轮已明确要求「彻底 / 高可信 / 多跑」→ 直接按**建议 3 轮**跑，仅补报一句规模。
- **不读** `~/.config/opencode/shy-models.md`、不新增自有配置文件、不依赖 `shy-setup-models`（保持轻量）。

**多跑口径**：

- **裁决**：**必须配独立裁判**——用**主代理模型 + 盲评**（独立上下文、不看跑次标签）逐条复核；产出标**票数**（`3/3`、`2/3`、`1/3`），**共识优先采信、独报标「需复核」**。
- **并发降级**：支持并发 → 并行；不支持 → **串行**（延迟 ×N，先告知用户）；子代理都不可派 → **内联**并在报告标注「未隔离（独立性打折）」（见 `subagents.md`）。

**成本口径**：3 轮 = 剪枝 3 + 有效性 3 = **6 个评审子代理** + **1 个独立裁判**。

### Step 0 · 立靶（跳过这步，后面全是空谈）

读对应需求文档 `docs/<skill>/requirements/REQ-NNNN-*.md`，明确"本技能要改变什么行为"，作为复审基准：

- **有 REQ** → 直接用。
- **无 REQ** → 问用户能否说清意图：**能** → 按 `grilling.md` **从意图**问出来，落一份**回溯补写**的 REQ（见 `writing-requirements.md`），再复审；**不能** → 记下 `no spec available`，Spec 轴（Step 3）跳过。
- **禁止读技能反推 REQ**（循环论证，会让 Spec 轴变成橡皮图章；回溯补写见 `grilling.md`）。

同时记录技能文件集与常驻的 `description`。

**完成判据**：手里有 1 份"要改变什么行为"的基准（REQ，或明确记下 `no spec available`），且技能文件集与 `description` 已列出。

### Step 1 · 触发审查（最高价值：触发错了，技能等于不存在）

`description` 是唯一的触发指针，它措辞的精度决定技能何时被想起。

- **该触发的触发了吗**：覆盖真实用户会说的说法——口语、错别字、缩写，以及**不点名域名的说法**（用户说的是需求，不是技能名）。
- **不该触发的没触发吗**：重点看 **near-miss**（共享关键词但任务不同），这才是过宽的信号；"问天气"这类无关查询测不出任何东西。
- **措辞**：按 [`writing-skills.md`](writing-skills.md) §1 的 description 写法核对（祈使句 / 聚焦用户意图 / 边界宁可 pushy）——此处只检查，不复述。
- **硬约束**：按 [`writing-skills.md`](writing-skills.md) §1 核对（长度 / 命名），此处不重复数值。
- **调用方式选对了吗**：按 [`writing-skills.md`](writing-skills.md) §1 的调用方式规则核对（选错是持续的上下文浪费）——此处不复述判据。
- **与相邻技能的边界**：是否有职责重叠、互相抢触发。

**怎么验**：构造 8–10 条 should-trigger 与 8–10 条 should-not-trigger（含 near-miss）查询，各跑多次算**触发率**；把查询分成 train/validation 两半，只用 train 的失败去改措辞，用 validation 判断是否泛化——防止把描述过拟合到测试句子上。（可执行：`generate_eval_set.py` 生成起手集、`optimize_description.py` 打分选优，见 `running-evals.md`；子 agent 版见 `subagents.md` 的 executor。）

**迭代停止规则**：通常 **5 轮足够**；卡住时**换一种结构性写法**（例如从"列举分支"改为"按用户意图收口"），而不是继续微调措辞——继续微调是把 description 过拟合到测试集。

**完成判据**：描述符合硬约束；**有指纹匹配当前技能的触发证据则引用并标注来源，无则标「（静态）待验证」**——不再硬性要求本轮跑出触发率（取证另由 `/shy-skill-eval` 按需触发）。

### Step 2 · 有效性审查（技能是否真的改变了行为）

**默认静态 + 按指纹引用证据**：同技能工作区存在**指纹匹配当前技能**的整技能对照（`evidence.json` 的有效性轴）→ 引用该 delta、标注来源（哪一轮 `iteration-N`）；**无匹配证据**（不存在 / 指纹不匹配 / 无 `evidence.json` 的旧证据）→ 有效性轴标「（静态）待验证」或「过期证据（技能已变更）」，**不自行静默跑 eval**（取证由用户触发 `/shy-skill-eval`）。取证口径：取 2–3 个真实 prompt，各跑**有技能 / 无技能**两遍（改进已有技能时，用旧版快照作基线），比较通过率与 token / 耗时。（工作区布局、产物 schema 与 `aggregate_benchmark.py` 见 `running-evals.md`；子 agent 版见 `subagents.md` 的 executor + grader。）

**case set 的来源**：**全部 `in-progress` / `done` REQ** 里标 **`（行为）`** 的验收标准的并集（分类见 Step 3；未实现 / 延后 / 不做的是未来契约，不计证据）——这样"旧 REQ 的行为今天还成立吗"由同一次对照回答，不额外付费。不要只取本次 REQ 的：行为类回归与 Spec 轴走同一份并集。

然后对每条指令追问：**"没有这句，agent 会做错吗？"** 不会 → 它是 no-op 或 cache（定义见 `writing-skills.md` §7）——**删除项归标准轴 Step 4 报一次，本轴不重复列**；本轴只记"该内容不买行为改变、有效性缺证据"。

- **真实专长（AI 生成技能的头号风险）**：技能里有多少内容是**这个项目 / 领域独有、且模型推不出来**的？若整篇换成任何同类项目仍成立，就是通用废话（"handle errors appropriately"），必须回填真实材料——真实任务步骤、runbook、事故与修复、代码评审意见、diff。
- **gotcha 是否缺失**：最值钱的内容是**反直觉的项目事实**（软删除要加 `WHERE deleted_at IS NULL`、同一 ID 三个服务三个叫法）。轨迹里 agent 犯过的错、你纠正过的地方，回填成 gotcha——这是最直接的迭代改进。
- **事实准确性**：版本号、API 名、参数、外部链接是否过期或写错——过时事实比缺失更有害。
- **粒度 / 控制力度 / 默认 vs 菜单 / 教方法** → 见 `writing-skills.md` §9、§10。

**完成判据**：每条指令都过了"没有它会做错吗"，且能指出它防住的具体错误；有效性轴**有指纹匹配的 delta 证据则引用、无则标「（静态）待验证」/「过期证据」**。**启用多跑时**：内容发现类候选按「成本闸门 · 按需多跑」取并集并交独立裁判（产出标票数，共识优先、独报标「需复核」）。

### Step 3 · 需求一致性审查（Spec 轴）

这是**记账层，不是第二次测量**：本步只负责**把验收标准映射到证据**。可外派给 `subagents.md` 的 **spec-reviewer**（独立于作者）。

**范围 = `in-progress` / `done` REQ 的不变量集 + `（未定）`项；`（episode）` 不读。**（未实现 / 延后 / 不做的是未来契约，不计证据。）

**范围收口**：基准只有**技能文件**与各 REQ 的 `## 验收标准`。REQ 的 问题与目标 / 行为与步骤 / 范围外 / 备注 是**冻结历史**——过期不是 finding。候选 finding 的 `location` 必须落在技能文件或 `## 验收标准` 行；引用历史散文的候选**直接丢弃**（否则就是"复审循环"本身）。

- **不变量集**（`check:` + `（行为）` + `（语义）`）：每轮跑 / 判。
- **`（episode）`**（一次性事实）：**冻结、不读、不复扫**。
- **`（未定）`**（尚未分类的存量）：**读到即分类**——读到的每条**立刻判**成 不变量 / `（episode）` / 真·未定，并写下决定。**不允许"读一遍、标个 `migration`、原样留下"**——那等于每轮重读同一批，债永不降。分类后：不变量进不变量集、`（episode）` 冻结、仍判不准的才是真·未定。

**债是进度条**：未分类债 `untagged` **单调降到 0**，每轮读的是**剩下的**，不是全部。**归零那天 Step 3 范围 = 不变量集**，`（episode）` 不读——**这才是 A（复审循环）的消失点，且可验收（`untagged = 0`）**。

**为什么不再是"无条件全量扫"**：历史工单已冻结，重扫它们的散文正是"复审→修补→新问题"循环的来源；且"这次改动影响哪几个 REQ"**无法机械计算**（验收标准与实现无登记对应）。所以不按改动定范围，而按**分类**定范围（不变量 / episode / 未定）——范围随迁移单调收缩，但**永不重扫已冻结的 episode**。

**默认靠跑，不靠读**：

1. **先跑**：`python "<SKILL_DIR>/scripts/run_checks.py" --root . --skill <skill>`——把全部 `check:` 一次跑完（秒级、结果固定），末尾给出 `（episode）` / 未标（= 迁移债）/ 台账 open 计数。失败即**真回归**（P0/P1）。
2. **再分派**：`（行为）` 落 Step 2 的 with/baseline；`（语义）` 与 `（未定）` 逐条读、判**通过 / 部分 / 未实现**，并**引用 REQ 那一行**。
3. **不自扫自洽项**：不改变行为契约的陈述一致性（计数漂移、措辞、重复）**不是验收标准**——**进 `cleanup.md` 台账**（有 id / 关闭路径），不进 findings、不阻断。注意与「文档-实现不一致」的区别：后者是**行为**对不上（触发分支 / 范围外 / 接口语义），仍要报。

**唯一豁免**：本次增量**只改了 REQ 文档、未动技能文件**时可跳过，但须在报告里注明"未做 Spec 轴"。

**降级**：无 REQ 且未回溯补写 → 标 `no spec available`，只做 `description` / 声明 ↔ 实现的**自洽检查**，并注明降级。

**成本杠杆**：把验收标准**写成可执行的**（`check:`，见 `writing-requirements.md` §4），以及**降频不降范围**（把不变量集扫描绑在用户选定的复审时机）。

报四类 finding（基准是**不变量 / 技能文件**，不是历史散文）：

- **缺失 / 部分**：不变量要求了但没做，或只做了一半。
- **范围蔓延**：实现里有不变量 / 技能文件没要求的行为（多出的分支、章节、脚本、参数）。
- **看似满足但行为不对**：验收项打了勾，实际行为不符。
- **文档-实现不一致**（技能特有，基准为技能文件）——**只在会误导 agent 行为时才算 finding**：
  - `description` 与路由表 ↔ 技能文件里的分支；
  - 技能文件声明的范围 ↔ 实现有没有偷偷做；
  - 技能文件声明的脚本 / 接口 ↔ 文件是否存在、参数 / 返回 / 失败语义是否一致。
  - 旧 REQ 的**文字过期**（其检查仍绿、仅措辞落后）→ 台账类，见 Step 8 材料性门槛。

**完成判据**：`run_checks.py` 全部 `check:` 项通过（失败项已列为 P0/P1）；全部 `（行为）` 项按 `running-evals.md`「指纹」的规则处理（证据匹配则引用，否则标「（静态）待验证」/「过期证据」）、`（语义）` 与 `（未定）` 项有判定（通过 / 部分 / 未实现）+ 证据；`（episode）` 不读。**`converged` 要求迁移债达标**（`untagged` → `state.json` 的 `debt_targets`）。范围蔓延与文档-实现不一致各给出结论（无则明说"无"）。唯一豁免情形须在报告注明。

### Step 4 · 结构与预算审查（信息层级）

逐条按 `writing-skills.md` 检查：**§3** 信息层级与按需披露、**§4** co-location、**§5** leading word、**§6** 否定句、**§7** 剪枝（单一事实源 / cache / relevance·sediment）。

**与行为轴的分工（同一 no-op 只报一次）**：本步是三条轴里**唯一的"内容该删"出口**——no-op / cache / sediment / 重复的**删除项都在本步处置**（按 Step 8 材料性门槛分流：影响使用的进 findings，其余登记 `cleanup.md`、由主 agent 当轮结清）；行为轴（Step 2）只从效果侧记"该内容不买行为改变、有效性缺证据"，**不重复列删除项**（两轴都会看到同一批内容，但 finding 只落一处）。

**完成判据**：`SKILL.md` 在预算内；每条下放内容都有触发它的指针；无重复（单一事实源被破坏）/ cache / sediment。若行为轴已就同一处内容报过"有效性缺证据"，本步给出**唯一的删除处置**（findings 或台账），不另开一条。**启用多跑时**：删除候选按「成本闸门 · 按需多跑」取并集并交独立裁判（产出标票数，共识优先、独报标「需复核」）。

### Step 5 · 步骤与完成判据审查

逐条按 `writing-skills.md` §8 检查：完成判据（可判定）、判据强度、抢跑、破坏性 / 批量操作的验证回路。

**完成判据**：每个 step 都能指出其完成判据，且判据可判定。

### Step 6 · 脚本与资源审查

- **非交互**：脚本从参数 / 环境变量 / stdin 接收全部输入（等待 TTY 会挂死）；缺参时给出带用法的清晰报错。
- **`--help` 完整**：简述 + 参数 + 示例 + 退出码含义——这是 agent 了解接口的主要途径。
- **错误可行动**：说清"哪里错、期望什么、下一步试什么"，而不是 `invalid input`。
- **输出结构化**：优先 JSON/CSV；**数据走 stdout、诊断走 stderr**，便于管道消费。
- **幂等**：agent 会重试，"不存在则创建"优于"重复即失败"。
- **安全默认与输出规模**：破坏性操作要 `--confirm`/`--force`；大输出默认摘要并提供 `--offset`/`--output`，避免被工具层截断丢失关键信息。
- **依赖与版本**：脚本是否自包含或明确声明依赖、是否需要固定版本；技能是否需要 `compatibility` 声明运行前提。
- **该固化的逻辑**：轨迹里 agent 每次都在重造同一段逻辑（画图、解析、校验）→ 写成脚本放进 `scripts/`，一次测试、反复复用。

**完成判据**：脚本逐项过了本步清单——非交互、`--help`、结构化输出、幂等、输出规模可控；且**被审技能自己有测试覆盖**：跑其自带的测试（如 `scripts/test_*.py`）到退出码 0（每个脚本 ≥1 条成功路径 + ≥1 条失败路径契约用例），无测试则要求其说明为何不需要。（**不要**用本套件的 `selftest.py` 代替——它只测套件自身，证明不了被审技能。）

### Step 7 · 安全、边界与自包含审查

- **来源与网络**：是否有可疑的外部网络访问、数据外泄指令、未声明的依赖或捆绑资源；安装来源是否可信。
- **凭据**：技能文件里不得出现密钥、token、个人路径等敏感信息。
- **破坏性护栏**：改用户内容前是否备份 / 可回退 / 先确认。
- **能力降级**：平台差异、缺失能力、降级路径是否写明（如某格式不支持某语法时的替代写法）。
- **自包含**：技能文件只引用技能自身（相对技能根），不引用仓库级 `docs/` 等外部路径——技能会被单独复制部署，外部引用就是悬空指针。（这里指**技能文件内的链接**；本套件工作流运行时要读写 `docs/<skill>/…`，那是**开发仓库**的用法，不算违反——技能单独部署后这些 `docs/` 不存在，按「非开发仓库」降级。）

**完成判据**：来源、凭据、破坏性护栏、能力降级逐项过；自包含检查无悬空引用。

### Step 8 · 汇总裁决

把发现归入三档，并给出结论：

| 结论 | 条件 |
| --- | --- |
| **可合入** | 无 P0 / P1，触发 / 有效性 / 需求一致性证据通过（或已注明未做 Spec 轴）；**P2 不阻断** |
| **改后可合入** | 存在 P0 / P1 可定位、可修复的问题 |
| **需重做** | 触发或核心行为错误、严重偏离需求，或安全问题 |

**报告格式**（HTML 是给人看的，每条一行，不复述技能内容）：

```
[轴] [优先级] 位置 — 存在问题 → 白话解释 → 修改建议
```

- **报告只渲染三字段**：`problem` **存在问题**（专业、简短，含"为什么要改 + 改后好处"）、`plain` **白话解释**（一般人能懂的话）、`suggestion` **修改建议**（怎么改）。`falsification` / `evidence` 是 **agent 的过程字段**——留在 `findings.json` 供审计，**不进 HTML**。
- **证据来源与降级条**：报告标注行为轴证据来源（哪一轮 `iteration-N`、**指纹匹配** / 「（静态）待验证」/「过期证据」）；**无匹配证据时显示降级条**——不把静态判断伪装成实测，也**不因缺 eval 而拒绝收工**（复审默认静态）。
- **淘汰数与过程字段的关系**：`summary` 的**淘汰数（候选 / 通过 / 被证伪）是汇总行、保留可见**；不进报告的只有逐条的 `falsification` / `evidence`。两条规则不冲突。
- **轴**：`行为`（触发 / 有效性）/ `需求`（Spec）/ `标准`（结构 / 脚本 / 安全）——**分轴报告、不合并**：一条轴过、另一条败是常事，合并会互相掩盖。
- **优先级**：`P0` 阻断（触发错误 / 行为错误 / 偏离需求 / 安全）→ `P1` 行为提升 → `P2` 精简与可读性。
- **P2 不阻断，自洽项进台账，机械项由主 agent 当轮结清**：`P2`（精简 / 措辞 / 数字漂移 / 重复）**不阻断 `done`、不新开 REQ**；其中"文档 / 措辞自洽"类（Step 3 第 3 条）**不进每轮 finding**——**写进 `docs/<skill>/cleanup.md` 台账**（id / dedup_key / 关闭路径）。复审的"发现"由**子代理**做（独立性），但子代理**禁写**（见 `subagents.md`）；**结清由主 agent 在 Step 8（出报告前）当轮完成**：
  - **机械可修**（当轮结清、标 `fixed` + `evidence`）：去重 / 改指针 / 行号订正 / 死字段删除 / 计数漂移等**不改行为**的文本与卫生项；**改前查引用、改后过 Gate**。
  - **需决策**（留 `open`）：设计取舍 / 跨较大改动 / **会改 Gate 行为**（如接线新字段）/ 需用户拍板；在报告里**一句话提示**，不占 findings、不阻断。
  只有 `P0` / `P1` 才要求"改后可合入"。
- **findings 门槛（材料性）**：候选只有**不修会让用户 / agent 做错事或做不成事**（行为 / 触发 / 接口 / 安全 / 可用性）才算 finding；以下属**台账类**——写进 `cleanup.md`、**由主 agent 当轮结清（机械项）**、不进 findings：过期验收文字（其检查仍绿、仅措辞落后）、提示文案偏差、重复、措辞、死代码、自洽计数。
- **语义集做减法**：稳定 ≥2 轮、且内容已被技能文件或检查覆盖的语义验收 → 标 `（episode）` 冻结，缩小下轮复审面。
- **脆弱性收敛判据**：一次复审 **0 P0/P1** 且 **0 条"上轮改动涟漪"类 finding**（新 finding 均不落在上轮改过的文件 / 契约上）→ **脆弱性已解**；只记结论、不排下一轮，直到真实失败 / 用户显式要求再开。
- **`converged`（机械判据，非 agent 自证）**：定义见 `glossary.md`——由脚本算出、agent **不得手写**。达标的唯一动作是把 `converged_since` 记进 `state.json`，**不排下一轮**；只有**真实失败 / 用户显式要求**才重开。
- **说人话（报告是给人看的）**：`problem` 专业简短；`plain` 用白话讲清"这是什么、为什么要改、改了会怎样"。**人类字段里不得出现未解释的 `§` 章节引用、内部术语、裸 `file:line`**——要提就一句话说清它是什么（写"§5"就要写成"《技能需求规范》里那条复审范围规则"）。读者是用户，不是替你复现推理链的人。术语用 `glossary.md` 的写法。

可选：把 `benchmark.json` / `grading.json` 交给 `subagents.md` 的 **analyzer** 做失败聚类、flaky 与回归分析。可选（主观型技能、比两版时）：用 `subagents.md` 的 **comparator** 做盲测 A/B，**与断言结果并列报告**。

**完成判据**：给出三档结论之一；改进清单已按 §3「先证伪」筛过，并在 `summary` 附**淘汰数**（`candidates` / `passed` / `falsified`）；产出 `findings.json` + **HTML 报告并打开**（默认自动打开，见 `running-evals.md`）；**若 0 P0/P1 且迁移债达标 → 把 `converged_since` 记进 `docs/<skill>/state.json`（`converged` 只读 `run_checks.py` 输出，agent 不得手写）**；然后**逐条请用户分拣**（选项见 `glossary.md`「分拣」；**不做批量**；`--serve` 模式下报告末尾点「提交给 agent」（静态报告只读、不自动回传），见 `lifecycle.md` 阶段 3；**回写按 `triage.json` 每条的 `location` 对应 `findings.json`**——`id` 只是报告渲染顺序，与数组顺序不保证一致；**同一 `location` 有多条 finding 时**，按 `suggestion` 首句消歧），按所选实施一次后**结束**（见 `lifecycle.md` 阶段 3）。

**报告是终局产物**：**只在 Step 8 生成一次**，且由**主 agent**打开。复审中途（Step 1–7）不得生成报告——包括为验证渲染而跑 `render_report.py`（那会让浏览器在复审中途弹出来打断用户）。确需中途验证渲染，用临时工作区 + `--no-open`（或 `SHY_NO_OPEN=1`）。

**`findings.json`（呈现层数据契约，供 HTML 报告消费）**：

```json
{
  "skill": "<skill-name>",
  "iteration": 1,
  "generated_at": "<ISO-8601>",
  "verdict": "可合入 | 改后可合入 | 需重做",
  "summary": {"candidates": 0, "passed": 0, "falsified": 0},
  "evidence": {"status": "matched | static | stale", "iteration": "iteration-N | null", "detail": "（可选）一行说明"},
  "findings": [
    {
      "axis": "行为 | 需求 | 标准",
      "priority": "P0 | P1 | P2",
      "location": "file:line",
      "problem": "存在问题（专业简短，含为什么要改 + 改后好处）",
      "plain": "白话解释（一般人能懂）",
      "suggestion": "修改建议（怎么改）",
      "falsification": "推翻它要跑的命令 / 原文",
      "evidence": "已跑结果",
      "verified": true
    }
  ]
}
```

- 位置：`<skill>-workspace/iteration-N/findings.json`；纯复审无 eval 时 `<skill>-workspace/findings.json`。
- `verified: false` 的条目仍进报告，但标注「待验证」（对应 §3「跑不了检查的只标待验证」）。
- `evidence` 驱动报告顶部的**行为轴证据来源 / 降级条**（Step 8 同名条）：`matched`（指纹匹配）绿条；`static` / `stale` / 缺失 → 黄条「（静态）待验证 / 过期证据」。**不复用逐条 finding 的 `evidence`（已跑结果）字段**。

## 3. 如何提出改进意见（让意见真的有用）

- **先证伪，再提**：每个候选意见，先问"**哪条命令、哪段原文能最快推翻它？**"，**跑完再写**；被推翻的丢弃。跑不了检查的标「待验证」，随报告呈现但**不计入淘汰数的「通过」**。依据写"**我看到 X**"，不写"我认为 X"。
- **报告淘汰数**：写明"N 个候选，M 个通过，其余被证伪"，让筛选可见。
- **先删后加**：提新增前先问"这是不是已有内容的重复或补丁"。
- **泛化，别打补丁**：修的是底层类别，不是测试集里的那句特例。把失败查询的**关键词**抄进 `description` 就是过拟合——要找它代表的类别。
- **给 why**：解释性指令（"做 X，因为 Y 会导致 Z"）比硬规则更可靠。
- **可落地**：说清改哪里、改成什么、预期行为怎么变；只给"这里可以更好"不是意见。
- **过约束就做减法**：加规则后通过率不升反降，说明约束过头，应删规则再测。

## 4. 复审自身的反模式

- **静态打勾不跑**：不看真实轨迹的复审，必然漏掉真正的失效（绕路、误触发、抢跑）。
- **只审 `SKILL.md`**：不看 `scripts/`、`references/`，也不看真实触发，等于只审了技能的三分之一。
- **把 Spec 轴并进质量轴**：需求一致性一旦与"结构/脚本好不好"混着报，就会被淹没——分轴是刻意的。
