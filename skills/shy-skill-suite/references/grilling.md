# 逼问（grill）

把模糊想法逼成明确需求——无论是新技能，还是给**既有技能**回溯出意图（无 REQ 时）。

## 机制：设计树 + frontier

- 把要做的技能看成一棵**设计树**：每个决策分出下级决策。
- **frontier** = 前置已定、现在就能问的那批决策。**一轮问完 frontier**，每问**附上你的建议答案**，等用户回答后再算下一轮。
- **事实自己查**（读仓库、跑命令、派子 agent），只把**决策**留给用户。
- 依赖尚未回答的问题，留到**后一轮**，不要这轮就问。

## 技能领域要问透（每项都要能落到验收）

- 这个技能**改变 agent 的什么行为**？（一句话）
- 用户会**怎么说**才触发它？不点名域名的说法是什么？
- 边界：**相邻技能 / 内置能力**是什么，怎么不抢触发？
- 验收**证据**是什么？（触发率？对照 delta？输出形状？）
- **范围外**明确不做什么？
- 依赖与降级：平台差异、缺能力时怎么办？

## 三个动作（吸收自 `domain-modeling`，只取动作、不引入其文件结构）

1. **术语规范化**：用户用模糊或过载的词时，逼出精确说法——"你说的'整理'是指分类还是合并？"；有既有技能 / 术语表就对照，冲突当场摆出。**定下即落盘**：套件自身的词 → `references/glossary.md`；被开发技能的词 → `docs/<skill>/glossary.md`（按需创建）。每条 = `术语` / 一行白话 / `_避免_`（不再用的说法）。
2. **场景压测**：拿**具体输入与边界案例**追问——"对话里有两个主题，你会拆吗？"
3. **与实现交叉核对**：用户说"这技能会 X"，就去**现有技能文件**里核对；矛盾就摆出来（"文件里没有这条分支"）。

## 完成判据

**frontier 空** = 每个分支都问过、没有静默假设，且**用户确认理解一致**，才进入下一步。

## 可跳过

**是否逼问按来源判**：判定表见 [`lifecycle.md`](lifecycle.md) 阶段 1（单一事实源），本文件只讲怎么逼问。跳过时在 REQ 备注记 `逼问：跳过（依据：…）`。

## 用于回溯补写（既有技能、无 REQ）

**不要读技能反推需求**（循环论证、橡皮图章）。改成**从意图问出来**：把上面的问题对着用户问一遍，产出的是"这技能**应该**改变什么行为"，而不是"它现在做了什么"。落 REQ 时标 `retroactive: true`。
