# 智识沉淀（对话总结为笔记）

## Overview

将一段对话沉淀为可长期使用、可检索复用的知识库条目：完整保留有价值细节，按分类归档到独立的 `AI笔记` 根目录，用链接关联已有笔记（Obsidian 双链 / 普通 Markdown 标准链接），并自动维护每个分类的索引文件。对话较长、涉及多个相互独立的主题时可拆分为多篇笔记，偏保守拆分、先给方案一次确认后分别生成。

**分支路由**（按用户意图进入对应章节）：

| 用户意图 | 章节 |
| --- | --- |
| 把对话总结成笔记 / 保存为笔记 / 沉淀到知识库 | 下方工作流程（Step 0 起） |
| 修改智识沉淀设置 / 变更保存位置或格式 / 重新配置目录 | 「配置修改」 |
| 查找、检索之前记过的笔记 | 「检索已有笔记」 |
| 检查笔记库 / 断链 / 索引对齐 / 整理笔记库 | 「健康检查」 |
| 给某主题做知识地图 / MOC / 聚拢散落笔记 | 「生成内容地图（MOC）」 |

**最高原则（务必遵守）**：

- **沉淀而非压缩**：为简洁而砍掉细节是错的。只剔除与主题无关的寒暄/闲聊，主题相关的详细内容原样保留（要保留的细节清单见 Step 6「落到具体」）。
- **绝不编造事实（红线）**：内容忠实于对话实际给出的信息，不虚构、不补全、不美化、不改写事实（数据、数字、版本、人名、时间、事件、结论等）。对话未给出、也无法由对话推出的信息，标 `(待核实)` 或留白并询问用户——宁可笔记缺一块，也不填一个"看起来合理"的说法。事实与推断的区分、易变事实加日期、外部事实核验等具体规则见 Step 6「真实性」。
- **外部引用标注来源**：引用对话之外的外部事实（版本号、政策、数据、外部事件）时注明出处，并区分「对话内观点」与「外部核验事实」；无法核实的标 `(待核实)`。
- **表达风格随内容与指令定**：优先级为「当次明确指令 > 本次会话已确立风格 > 笔记默认体例」，详见 Step 6「表达风格与讲解方式」。

## 脚本调用约定（重要）

本技能所有脚本命令**一律用绝对路径调用**（如 `python "<SKILL_DIR>/scripts/skill_tools.py" <子命令>`）——技能的运行工作目录通常是用户的会话目录，而非技能目录，相对路径会直接失败。

**技能目录解析**：`$TELEAGENT_CONFIG_DIR/skills/knowledge-distill`（`TELEAGENT_CONFIG_DIR` 缺省为 `~/.config/TeleAgent`）。本文档后续用 `<SKILL_DIR>` 代指该目录。

- **推荐写法**（先解析出技能目录，再拼绝对路径）：

  ```bash
  python "<SKILL_DIR>/scripts/skill_tools.py" <子命令> [参数]
  ```

  例：`python "C:\Users\<用户>\.config\TeleAgent\skills\knowledge-distill\scripts\skill_tools.py" load-config`
- **Windows PowerShell**：调用前先设置 `$env:PYTHONUTF8="1";`，避免中文路径与内容编码错误。
- 路径含空格时必须加引号。
- 若不确定技能目录位置，先用文件搜索定位 `skill_tools.py`，再使用其绝对路径。

## 工作流程

### Step 0：读取配置与目录情况

1. 运行 `python "<SKILL_DIR>/scripts/skill_tools.py" load-config` 读取持久化配置。
2. 若配置中有 `vault` 和 `note_root`，先运行 `python "<SKILL_DIR>/scripts/skill_tools.py" list-structure "<vault>\<note_root>"` 查看已有分类与笔记，作为后续判断依据。
   - 返回结果中每个分类含 `notes`（真实笔记）与 `has_index`（是否已有索引文件）两个字段；`00-分类索引.md` 是索引文件，用 `has_index` 标记、不出现在 `notes` 里，新建/合并判断只针对 `notes`。

### 配置存在时的流程（第二次及以后保存）

直接复用配置中的格式与目录，跳过首次配置，从 **Step 3 主题切分** 开始执行。**每次保存都明确告知用户保存到了哪个 vault/目录，并提醒"可通过说明'修改智识沉淀设置'来变更保存位置"。**

### 首次触发（无配置）流程

#### Step 1：确认笔记格式

询问用户的笔记格式，三选一：**Obsidian**（推荐）、**普通 Markdown**、**其它**。

- **Obsidian**：运行 `python "<SKILL_DIR>/scripts/skill_tools.py" discover-vaults` 发现本机 vault。
  - 发现到多个 vault → 列出并询问用户保存到哪个。
  - 发现到单个 vault → 直接采用。
  - 未发现（未装 Obsidian / obsidian.json 不存在）→ 让用户手动填写 vault 绝对路径。
- **普通 Markdown / 其它**：直接询问用户保存目录（绝对路径）。

> 注意：用户机器上可能没有 Obsidian，若无法自动发现且用户也不确定 vault，可推荐用户先明确保存目录，或选普通 Markdown。
>
> 两种格式的差异与完整写法：Obsidian 见 `references/obsidian-best-practices.md`，普通 Markdown 见 `references/plain-markdown-best-practices.md`。写入前按所配格式查阅对应文件。

#### Step 2：确定并保存配置

1. 确认最终 `format` 与存储位置（vault 或目录）。
2. 笔记根目录名默认 `AI笔记`；若所选目录下已存在 `AI笔记` 目录则直接复用，否则在保存时创建。
3. 将配置写入文件（**推荐用 `--config-file` 传 JSON 文件路径**，避免命令行引号转义问题）：

   ```bash
   python "<SKILL_DIR>/scripts/skill_tools.py" save-config --config-file <临时json文件>
   ```

   配置结构示例：

   ```json
   {"format": "obsidian", "vault": "D:\\示例路径\\我的笔记库", "note_root": "AI笔记"}
   ```

   普通 Markdown 时用 `"directory"` 字段代替 `"vault"`。

### Step 3：主题切分与方案确认（关键决策点）

**本技能支持将长对话按主题拆分为多篇笔记**，而不是固定总结到同一篇。

**核心原则：所有询问默认在本步集中完成**（避免一篇笔记来回确认 2-3 轮）；后续步骤按确认结果执行，只在遇到方案表未覆盖的新情况时单独询问那一项。

1. **判断是否需要拆分**：AI 通读整段对话，识别存在哪些**相互独立、各有价值**的主题块。
   - **默认偏保守**：只有主题差异明显、且内容**足够充实、独立成篇才有价值**时才拆分；碎片化、几句话的小话题不单独拆。
   - **同主题合并**：同一主题下的不同维度（如"实现过程"与"踩坑经验"）**合并进同一篇**的不同章节，不拆。
   - **异主题才拆**：仅当主题间差异大、关联弱、各自内容充实时才拆成多篇。
   - 单一主题的对话 → 维持单篇，同样走第 2 步的方案表。
2. **一次性给出完整方案表**：结合 Step 0 的 `list-structure` 结果（已有分类、已有笔记），为**每一篇**拟定标题、分类、新建或合并、一句话概要，合并成一张表让用户**一次性确认或调整**：

   | # | 笔记标题 | 分类 | 新建/合并（含合并方式） | 一句话概要 |
   | - | -------- | ---- | ----------------------- | ---------- |
   | 1 | 示例标题A | 已有分类「技能开发」 | 新建 | 本次对话的技能设计方法 |
   | 2 | 示例标题B | 新分类「示例分类」 | 合并至《示例笔记》（改写优化） | 本次对话的相关排查经验 |

   - **分类列**：优先归入已有分类并注明；无合适分类时给出新分类建议（避免与已有分类语义重复）；用户可自定。
   - **新建/合并列**：依据已有笔记标题与内容判断能否合并，注明合并目标笔记；判断不了时在该行标注"待确认"。
   - **合并方式**（仅合并行需给）：在方案表中一并给出**追加**或**改写优化**的建议，用户可逐行调整（详见 Step 5 合并规范）：
     - **追加**（保守）：只新增内容，不改动既有段落。适用于新内容是旧笔记之外的新信息。
     - **改写优化**：允许改写/替换/融合既有段落，使表述更详细、准确或生动（如补充类比）。适用于新旧内容重复、但新版本更优、用户希望优化原笔记。
     - 当发现新旧内容明显重复且新版本更详细/更生动时，**主动建议**"改写优化"，并说明理由，供用户选择。
   - 用户可回复：确认方案 / 全部合并为一篇 / 调整某行的标题、分类、新建或合并、以及合并方式。
3. **确认标题**：方案确认后，各主题的标题即文件名，应语义化、唯一。
4. 后续 **Step 4 ~ Step 8 对方案表中的每一行分别执行**（可各自归入不同/相同分类）；主题间若有相关性，跨笔记用链接互链。
5. 若方案表中存在"待确认"项，或执行中发现新情况（如目标文件重名、合并目标笔记内容不符），再**单独就该项询问用户**，不影响已确认的其它行。

**本步完成判据**：用户对方案表明确回复"确认"（或提出调整、调整后再次确认）后，Step 3 结束。未收到用户回复前停在方案表等待，不进入 Step 4。

### Step 4：确定分类（按 Step 3 方案表执行）

在笔记根目录下，**一级子目录即分类**。分类在 Step 3 方案表中已确认，本步只做落地：

1. 按方案表为每个主题块确定分类（优先归入已有分类；无合适分类则用确认的新分类）。
   - **避免分类碎片化**：新建分类前先确认确实没有已有分类可容纳。若已有分类语义相近（如"示例分类"与"示例"、"运维"与"运维经验"），优先归入已有分类，而不是再建一个。
   - 若发现已有分类明显重复或命名混乱，可在方案表中**建议**用户合并或重命名，但**不擅自改动**已有目录（改名/合并会牵动已有链接，需用户明确同意后单独处理）。
2. 对**首次创建的分类**：
   - 创建分类子目录即可。**索引文件无需在此手动复制**——Step 7 调用脚本时若发现索引不存在，会自动按 `assets/分类索引模板.md` 渲染创建（含 frontmatter、「笔记导航」「已收录疑问」章节，占位符与示例行一并处理）。
   - 若希望此时就建立索引，也可手动复制模板并替换 `{{分类名}}`；但**两种方式产出一致**，任选其一即可。
   - 无论哪种方式：模板的"笔记导航"表格**保持空表头**，具体条目由 Step 7 统一写入；模板中的示例说明文字（如"（此处分点记录…）"）替换为真实内容或删除。

### Step 5：执行"新建"或"合并"（按 Step 3 方案表执行）

新建/合并方式在 Step 3 方案表中已确认，本步按行执行：

1. **写前查重与文件名校验（必须，且必须在写笔记与更新索引之前）**：对每篇笔记先运行
   `python "<SKILL_DIR>/scripts/skill_tools.py" check-name "<分类目录>" "<标题>"`
   - `valid: false` → 标题含 `/` `:` `*` `?` 等非法文件名字符（含 `/` 时会被当成子目录、路径失真），**先按返回的 `suggested_title` 改名**再重试，或与用户确认新标题。
   - `exists: false` → 标题可用，记下最终标题，继续后续步骤。
   - `exists: true` → **先向用户确认三选一**：**覆盖** / **改名**（另取标题）/ **合并**进该笔记（走本步第 5 点合并规范）。
   - 注意 Obsidian 中同名笔记会让 `[[笔记名]]` 双链产生歧义，重名时建议优先改名，或改用 `[[分类/笔记名]]` 形式链接。
   - **本步确认的最终标题就是后续写入文件名与索引条目的标题**，三者必须一致；先查重再更新索引，可避免"索引已写入、笔记却改名"的不一致。
2. 在确定分类下（必要时跨分类）核对已有笔记（`list-structure` 已返回各分类笔记）。
3. **用内容检索判断能否合并**：仅看标题容易漏判，对本次主题的核心关键词运行
   `python "<SKILL_DIR>/scripts/skill_tools.py" search-notes "<note_root>" "<关键词>" [--category "<分类>"]`
   - 命中已有笔记且主题一致 → 方案表该行标为"合并至《目标笔记》"。
   - 无命中或主题差异大 → 新建。
   - 关键词不确定时可用 `--regex` 传同义词正则（如 `"关键词A|关键词B"`）。
4. **新建**：走 Step 6 撰写并写入流程。
5. **合并**（严格按以下规范，避免破坏已有内容）：

   **合并方式由用户在 Step 3 方案确认时逐行选定**（若 Step 5 才判定要合并，则此时单独询问用户），两种方式：

   | 方式 | 行为 | 适用场景 |
   | ---- | ---- | -------- |
   | **追加**（保守） | 只新增章节或段落，**不改动任何既有内容**；既有内容即使与本次重复也保留（可在新章节说明"补充"） | 新内容是旧笔记之外的新信息 |
   | **改写优化** | 允许**改写、替换或融合既有段落**，使表述更详细、准确或生动（如补充类比、补全细节） | 新旧内容重复，但新版本更详细/更生动，用户希望优化原笔记 |

   - **默认建议"追加"**；当发现新旧内容明显重复、且新版本更详细/更生动时，**主动建议**"改写优化"并说明理由，由用户决定。
   - **改写优化保留旧内容独有信息**：只改写/替换重复部分，旧笔记独有信息并入新表述或原样保留。改写保持原意、不引入无依据内容（仍受"绝不编造事实"红线约束）。
   - **改写优化 ≠ 消解冲突**：若新旧内容是**结论矛盾**（同一问题说法不一致），不适用"改写优化"覆盖旧结论，须按 Step 6「与旧笔记冲突时先标注」处理——显式标注两种说法及依据，确需改写旧结论时必须先经用户确认。
   - **元数据**：两种方式都保留原有 `tags`（可补充新标签），并追加/更新 `updated: YYYY-MM-DD`。
   - **插入位置**：追加时优先插到笔记末尾的"相关笔记"章节之前；若新内容明显属于某个已有章节，则插到该章节末尾。改写优化则直接在被优化的段落/章节处就地改写。
   - **来源标注**：合并的新内容可加一行来源说明（如"来源：2026-09-09 对话"），便于追溯。
   - **先确认再合并**：目标笔记内容与预期差异较大（可能被用户改过）时，先向用户确认再合并。
   - **写入方式**：先读取目标笔记原文、在内存中拼好合并后的完整内容，再用 `write-note` **整体写回**（见 Step 6）——脚本会先备份原文件、再原子替换，避免写到一半损坏原笔记。
6. 用户追问的相似问题 → 优先归入已收录该主题的那篇笔记，**不新建**。

### Step 6：撰写并写入笔记（核心，每个主题块分别执行）

按"知识库沉淀"原则撰写，对**每个拆分后的主题块**分别撰写一篇。要点：

- **落到具体**：方法、步骤、命令/代码、参数、配置、数值、结论依据、示例、注意事项、坑等写全，避免只留"解决了 X 问题"这类结论句。
- **聚焦用户疑问**：用户提问是疑惑集中点，完整呈现其解答与依据、延伸信息。
- **表达风格与讲解方式**（在"照搬口语"与"过度压缩"之间取中）：笔记文风随**内容与用户指令**定，不随对话的随口程度漂移。
  - **主基调篇内一致，明确指令优先**：一篇笔记只用一种叙述基调，不因某一轮对话的表述方式整篇改文风。用户明确说"这篇用白话写 / 写得严谨些"就照办；优先级为「当次明确指令 > 本次会话已确立的风格 > 笔记默认体例」；用户要求整篇用某风格时，就按该风格写主表述，不必再另堆一种写法。
  - **通俗解释按"是否新增理解路径"取舍**：对话中的类比、大白话、举例，若把抽象概念映射到具体经验、帮助建立直觉（例：用"按电梯按钮一次与多次结果相同"解释幂等）→ 保留；若只是换种说法重复同一句、删掉不损失理解 → 可略。尺度是"有无新增理解路径"，**不是**"越全越好"，也**不是**因"不够严谨"而删；通俗化只做加法或等价替换，保持原意。
  - **补充性通俗解释独立成块、与主表述并存**：用户只是要求"某个概念用白话再解释一下"时，把通俗版作为独立的提示块/小节保留，原有准确表述保持原样，主表述整篇基调不变——同一内容重复两遍才是冗余。提示块有明确标记，不视为"换腔调"，与"篇内基调一致"不冲突。
  - **呈现形式随格式**：Obsidian 用 callout（如 `> [!tip] 通俗理解`）；普通 Markdown 用 `> **通俗理解**：……`（普通 Markdown 不支持 callout）。
  - **风格要求本身不进笔记**："用户要求这样讲"属于对话过程，不构成知识，不写入正文（同 `references/obsidian-best-practices.md` 中"不谈 AI/LLM 话题本身"的原则）。
- **结构化**：标题层级、分点、代码块、表格组织清晰，便于检索。
- **按所配格式写入**：Obsidian 遵循 `references/obsidian-best-practices.md`，普通 Markdown 遵循 `references/plain-markdown-best-practices.md`（frontmatter 必填字段、链接写法、callout 替代、可写的语法子集等规则都在其中）。写入前先查对应文件。
- **关联**：文中提到的既有概念/笔记用链接关联，无法链到概念时保持内容自洽，后续可回补。本次拆分生成的多篇笔记若主题相关，在"相关笔记"章节互相链接。
  - **主动回链旧笔记（沉淀即检索）**：把 Step 5 用 `search-notes` 检索到的**同主题旧笔记**，在「相关笔记」章节回链，新笔记一落库就与既有知识连上；旧笔记这侧保持不动。
  - **Obsidian 格式**：只在本篇写**单向**双链 `[[笔记名]]`，反向链接交给 Obsidian 原生能力（Backlinks 面板与 Graph view）自动生成。
  - **普通 Markdown 格式**：无自动反链，需**手工补反向链接**——仅限 `AI笔记` 目录内的笔记，在末尾「相关笔记」章节补一行 `[标题](标题.md)`，只补本次实际引用到的关联；用户自己创建的笔记保持不动。
- **与旧笔记冲突时先标注、不静默覆盖（必须）**：撰写前用
  `python "<SKILL_DIR>/scripts/skill_tools.py" search-notes "<note_root>" "<主题关键词>" [--full]`
  拉出同主题旧笔记（加 `--full` 可看到完整正文），**由你判断**新内容与旧笔记是否**结论冲突**（同一问题说法不一致）。
  - 发现冲突 → 在**本次笔记**里用提示块显式标注冲突（Obsidian `> [!warning] 与 [[旧笔记名]] 存在冲突`；普通 Markdown `> **冲突提示**：与 [旧笔记名](旧笔记名.md) 存在冲突`），并简述两种说法各自的依据；同时在索引「已收录疑问」登记该疑问（Step 7），便于日后一次性回看裁定。
  - 若必须**改写旧笔记**才能消解冲突，**先向用户确认**，不擅自改动。
  - 说明：冲突判断属语义工作，脚本只负责把相关笔记取出来，判断与标注由 LLM 完成、结果显式可见——宁可把矛盾摆在明面上，也不要让知识库静默自相矛盾。
- **真实性（机制）**：
  - **区分事实与推断（必须）**：严格区分「对话里明确说的」与「AI 自己推的」，避免无依据内容混入知识库后被当成事实：
    - 对话中明确给出的 → 直接写，不加标记。
    - 由上下文推断得出 → 加 `(推断)` 标记，并在同一处简述推断依据。
    - 无法核实的外部事实 → 加 `(待核实)` 标记。
    - 依据：知识库最怕的不是缺失，而是看似完整但无依据的内容——后者会污染后续判断。
  - **易变事实标注日期（必须）**：涉及数量、版本、上线状态、进度这类会随时间变化的信息，写成 `……（as of YYYY-MM-DD）`，避免日后被误读为当前现状。与「区分事实与推断」互补：一个解决「可信吗」，一个解决「还成立吗」。
  - **上下文不完整时降级**：对话被截断、压缩或明显缺少关键信息（如命令只出现一半、结论没有依据）时，基于现有信息如实撰写，在缺失处用提示块标注——Obsidian 用 `> [!warning] 信息不完整`，普通 Markdown 用 `> **信息不完整**：……`——并说明缺什么、建议用户补充；必要时先向用户确认。
  - 宁可留白并标注，也不写看似完整但无依据的内容——后者会污染知识库，比缺失更有害。
  - **外部事实首选核验，且只核验不沉淀（必须）**：笔记中出现**客观的、可核实的、易失效或易错**的外部事实（如版本号、系统/产品名称、数据、指标、政策条款、外部事件时间等）时，若对话本身未给出充分依据、**且你对其准确性不确定**，**必要时调用搜索工具联网核验**，并把核验到的出处（来源名称或链接）标注在笔记中。
    - **仅高价值/易失效事实才搜**：只对"错了会影响使用、或已过时"的关键外部事实核验；方法论、经验、命令、排查思路等对话本身已讲清的内容，核验到此为止，避免拖慢沉淀。
    - **只验证不沉淀**：搜索只用于**核验准确性与标注出处**，笔记的知识来源仍是对话本身，搜索到的网页/文档内容不整篇或大段摘录进笔记（与 `references/design-boundaries.md`「外部资料 / 网页接入沉淀」一致）。
    - **标注方式**：核验后若与对话一致，可在该事实旁注明来源（如 `（来源：○○官网）` 或给出链接）；若搜索发现对话内容有误，按"与旧笔记冲突"一节的思路处理——在笔记中如实标注更正与依据，必要时询问用户；若搜索仍未能核实，标 `(待核实)`。
  - **超长笔记先分段草稿、再整体写入**：单篇内容很长时，先在临时草稿里分段补齐（避免一次性生成过长内容被截断），最后**整体**走 `write-note` 写入正式笔记。
- **写入文件（统一走 `write-note`，事务化写入）**：按 Step 5 确认的最终标题，先把完整内容写入一份临时草稿文件，再运行

  ```bash
  python "<SKILL_DIR>/scripts/skill_tools.py" write-note "<note_root>/<分类>/<标题>.md" --content-file "<草稿文件>"
  ```

  - 脚本会：目标已存在则**先备份**到 `~/.knowledge-distill-backups/`；先写同目录临时文件、再用原子替换（写到一半失败不会损坏原笔记）；内容与原文完全一致时返回 `unchanged`，不写、不备份。
  - 返回 `action` 为 `created` / `overwritten` / `unchanged`，`backup` 为备份文件路径（无备份时为 `null`）。
  - **所有整篇写入/重写都走本命令**（含 Step 5 的"合并"：读原文 → 内存拼好 → 整体写回）。Obsidian 用双链、普通 Markdown 用标准链接/相对路径组织。

### Step 7：更新分类索引文件

`00-分类索引.md` 以**笔记为单位**做导航，采用"去重聚合"策略。对**本次生成的每篇笔记**分别更新其所在分类的索引。

**用脚本写入表格**（保证列格式与链接写法稳定）：

```bash
python "<SKILL_DIR>/scripts/skill_tools.py" append-index-entry "<分类目录>" "<笔记标题>" "<一句话摘要>"
```

脚本会自动处理：文件不存在则按模板新建（结构与「Step 4」模板路径一致，含 frontmatter 与「已收录疑问」章节）、已存在同名条目则更新摘要、否则追加一行；返回值 `action` 为 `created` / `appended` / `updated` / `unchanged`。标题或摘要中的竖线、换行由脚本自动转义为表格安全形式，直接传原文即可。

- **链接写法随格式自动切换**（脚本读配置决定，一般无需干预）：Obsidian 生成 `[[标题]]` 双链；普通 Markdown 生成 `[标题](标题.md)` 标准链接。若配置缺失或需强制指定，可加 `--format obsidian|markdown`。
- 索引链接写法由脚本按配置生成，保持脚本产出即可（手工改动会在下次更新该行时被覆盖回配置格式）。

规则：

- **全新主题疑问** → 脚本追加一行（标题 + 一句话摘要 + 指向笔记的链接）。
- **相似/追问问题**（已收录在某笔记）→ **不新增条目**，只在对应笔记深化内容。
- 合并场景同样同步更新索引条目与摘要。
- 需要先查看当前索引时：`python "<SKILL_DIR>/scripts/skill_tools.py" list-index "<分类目录>"`。
- 若拆分后的多篇笔记分属多个分类，则分别对其所在分类调用脚本。

**「已收录疑问」章节**：该章节记录本分类覆盖到的关键疑问，每条**只放疑问 + 指向笔记的链接**（与模板注释一致），便于点击跳转。回答正文留在笔记里，索引只承载疑问与链接、由脚本写入，避免与笔记不同步。

**写之前必须先查重**（关键，避免"同义不同文"变成多条冗余）：

```bash
python "<SKILL_DIR>/scripts/skill_tools.py" list-questions "<分类目录>"
```

读取本分类已收录的疑问（返回每条疑问文本与已并列的笔记链接），逐条比对：

- 已有**语义等价**的疑问 → **复用该条的原疑问文本**再调用写入命令，脚本会命中该条并合并链接（复用原文本才能命中合并，另起说法会新增一条）；
- 没有等价的 → 作为新疑问写入。

写入：

```bash
python "<SKILL_DIR>/scripts/skill_tools.py" append-index-question "<分类目录>" "<疑问>" "<笔记标题>"
```

脚本统一生成 `- 疑问 → <链接>[、<链接>...]` 格式（Obsidian 为 `[[笔记标题]]`，普通 Markdown 为 `[笔记标题](笔记标题.md)`，读配置自动决定）；返回值 `action` 为 `appended` / `updated` / `unchanged` / `section_created`，`links` 为该疑问当前并列的全部笔记。

- **一条疑问可指向多篇笔记**：脚本对同一疑问**合并链接**（保留已有、追加新的、去重、保持顺序），既不覆盖已有指向，也不重复成多条。笔记按主题各自成篇，同一疑问若确实横跨多个主题，就把相关笔记**都列出来**，读者按需跳转。
- 若一条疑问已铺开到 4 篇以上（脚本会返回 `warning`），通常说明该疑问过于宽泛：宜拆成更聚焦的疑问，或确认这些笔记是否主题重复、可以合并。
- 只记录**用户真正提出过、且已在本分类笔记中解答**的疑问。同一疑问合并为一条。
- 疑问与笔记导航条目是两套视角：导航按"笔记"去重，疑问按"用户提问"去重，两者都要维护。
- 若某条旧疑问还是"纯文本回答、无链接"的旧格式，脚本会在下次写入命中它时自动规范为链接格式（回答本就应保留在笔记里，索引不重复承载）。

### Step 8：结果确认

1. **告知用户**保存结果：共生成几篇笔记，逐篇列出格式、vault/目录、分类、标题、完整文件路径；并提醒"可修改智识沉淀设置以变更保存位置"。
2. 若过程中任何判断不确定，**主动询问用户**，不擅自决定。
3. 若写入过程中出现失败（如权限、路径异常），如实告知用户并保留已完成的成果。
4. **顺带回报相关旧笔记（沉淀即检索）**：保存完成后，用本次主题关键词运行
   `python "<SKILL_DIR>/scripts/skill_tools.py" search-notes "<note_root>" "<主题关键词>"`
   把命中的**其它旧笔记**（分类 + 标题 + 路径 + 片段）一并列出，提示"这些旧笔记可能与本次相关"。
   - 这是把"沉淀"与"检索"接起来，用户不必再单独问一句"我之前记过什么"；只读检索，不生成任何新笔记。
   - 若本次笔记**已回链某篇旧笔记**，在该篇后注明"已互链"；若发现主题明显重合，可建议下次合并。

## 检索已有笔记

当用户问"我之前记过什么关于 X 的笔记""帮我找一下之前的笔记"时，不生成新笔记，只做检索与回报：

1. 读取配置拿到 `vault`/`directory` 与 `note_root`（`load-config`）；无配置则说明尚未保存过笔记。
2. 运行
   `python "<SKILL_DIR>/scripts/skill_tools.py" search-notes "<note_root>" "<关键词>" [--category "<分类>"] [--regex]`
   - 关键词不确定时用 `--regex` 传同义词正则；需要更精确时用 `--max-snippets`、`--context` 调整片段数量与长度；需要看到某篇笔记的**完整正文**时加 `--full`（用于读取旧笔记后带引用作答）。
   - 也可先 `list-structure` 看有哪些分类与笔记，再决定检索范围。
3. 向用户回报：命中的笔记（分类、标题、完整路径）与相关片段；**只读不写**，不修改任何笔记。
4. 若无命中，如实告知，并询问是否需要就当前内容新建笔记（此时才走 Step 3 起的保存流程）。

## 生成内容地图（MOC）

分类目录回答"笔记放在哪个抽屉"，MOC（Map of Content，内容地图）回答"关于这个主题我知道些什么"。当用户要求"给 X 做个知识地图 / MOC / 把散落的笔记聚到一起"时，按主题生成一页**跨分类**的链接清单：

```bash
python "<SKILL_DIR>/scripts/skill_tools.py" gen-moc "<note_root>" "<主题>" [--tag "<标签>"] [--keyword "<关键词>"] [--category "<分类>"] [--description "<说明>"]
```

1. **匹配规则**：优先用 `--tag` 按 frontmatter 标签精确匹配；否则用 `--keyword`（缺省为 `<主题>`）在标题、frontmatter、正文中做关键词命中；`--category` 可把范围限定在单个分类。
2. **输出位置**：写到笔记根目录下的 `MOC-<主题>.md`（与分类子目录同级）。因此 `list-structure` / `lint-notes` / `search-notes` 只处理分类子目录，**MOC 不会被误当作笔记，也不会报"未收录/孤立"**。
3. **可反复刷新**：MOC 由脚本生成，重复运行即重新聚合（已存在会先备份、再原子替换）；页面内也注明了"请勿手工编辑（下次生成会覆盖）"。
4. **按需生成**：仅在用户要求时生成 MOC。
5. **回报**：告知用户 MOC 文件路径、聚合到的篇数与各分类分布；若某篇相关笔记没被聚合进去，提示可换标签/关键词重新生成（笔记标题或标签变动后，重新运行 `gen-moc` 即可刷新）。

## 健康检查

当用户要求"检查笔记库 / 有没有断链 / 索引和笔记对不对得上 / 整理一下笔记库"时，运行只读检查并回报，**不自动修改任何文件**：

1. 读取配置拿到 `vault`/`directory` 与 `note_root`（`load-config`）；无配置则说明尚未保存过笔记。
2. 运行
   `python "<SKILL_DIR>/scripts/skill_tools.py" lint-notes "<note_root>"`
3. 脚本只报告问题、不改文件，返回八类结果，分「链接结构」与「内容质量」两组：

   **链接结构（五类）**：
   - `index_orphans`：索引「笔记导航」里收录、但文件已不存在（用户手删笔记后索引未同步）。
   - `broken_links`：笔记里的链接指向不存在的笔记（笔记改名后别处未更新）。
   - `unindexed_notes`：笔记存在、但所在分类索引的「笔记导航」里没有收录。
   - `orphan_notes`：既没有入链、也未被索引收录的孤立笔记（等于"写了但找不到"）。
   - `question_orphans`：索引「已收录疑问」里并列的链接指向不存在的笔记。
   - **链接兼容**：同时识别 `[[双链]]` 与 `[文字](笔记.md)` 两种写法，图片、外链、纯锚点会自动跳过，不会误报。因此 Obsidian 与普通 Markdown 两种笔记库都可用同一命令检查。

   **内容质量（三类）**：
   - `missing_frontmatter`：Obsidian 笔记缺 frontmatter，或 frontmatter 缺必填字段（`tags` / `created` / `source`）。**仅当用户已配置为 Obsidian 格式时检查**——普通 Markdown 无 frontmatter 要求，不会误报。
   - `empty_sections`：有标题、标题下却没有任何正文的章节（骨架写了没填）。
   - `stale_index`：笔记比其所在分类的索引文件更新（改了笔记、索引摘要却没同步）。
   - 返回的 `summary` 除 `issues`（问题总数）外，另含 `structure_issues`、`content_issues` 两个分组计数，便于一眼看出问题规模。
4. 向用户逐类列出问题清单（含完整路径），并**询问是否要修复**：
   - 索引类问题（`index_orphans` / `unindexed_notes` / `question_orphans`）可用 `append-index-entry`、`append-index-question` 等命令修正，但**必须先经用户确认**。
   - 断链的处置（改链接 / 补建目标笔记）由用户决定。
   - 内容质量类：`empty_sections` 需补齐正文、`missing_frontmatter` 需补字段，都走 `write-note` 重写该篇；`stale_index` 用 `append-index-entry` 刷新摘要。同样**一律先经用户确认再动手**。
5. 若八类问题均为空，明确告知"笔记库健康，未发现问题"。

> 设计取舍：只做**确定性检查**（文件存在性、链接目标、索引收录、frontmatter 字段、空章节、索引时效），不做语义判断，因此结果准确、可复现，适合脚本化。修改动作一律交回用户确认，避免误改用户内容。
