# shy-to-tickets

`to-tickets` 的强化封装。**上游技能是流程事实源**：先用 Skill 工具加载 `to-tickets`（失败则读 `~/.agents/skills/to-tickets/SKILL.md`），按它执行（gather context、探索、vertical slice 规则、wide refactor 规则、quiz 用户、发布），仅在「草拟切片」与「quiz 用户」之间插入盲评环。

分工依据：子代理看不见对话，**拆分不外包**；盲评拿两个机械可验的角度补漏——这比 to-spec 的裁决更接近实测。盲评者数取 3（三档票数，与对拍同一甜点）。

## 成本闸门（第 0 步：委派任何子代理之前）

盲评按子代理数量消耗 token（3 个盲评者 = **3 个子代理**）。**每次运行、委派前**先报规模并确认去向：

- 用户本轮已明确要求「盲评 / 覆盖检查 / 要质量」→ 视为已确认，报一句规模即执行；
- 否则**默认走原生轻跑**（按上游 `to-tickets` 原样拆分并发布，不加盲评），要用户主动选「盲评」才升级。

## 覆盖点

### 1. 物化 brief（草拟前）

把被拆分的需求逐行落盘（临时文件）：spec 原文的需求行（或对话里的决定），每行一行编号 + 原话引述。

### 2. 草拟（主代理）

照上游规则起草工单：标题 / 交付的端到端行为 / blocked by 边。

### 3. 盲评（3 个子代理）

并行、互不可见，输入 = brief + 工单草案，模型 = **三个不同模型各一**（ID 来源：用户级 `~/.config/opencode/shy-models.md`，由 `/shy-setup-models` 生成；文件缺失则先问用户并建议跑 `/shy-setup-models`，问不出再同模型凑满；某模型不可用则凑满 3 个：一模型 2 个 + 另一模型 1 个）。解析模型 ID 先查模型目录，看不到想要的加 `all: true`；不猜 ID。各出两份检查：

- **覆盖矩阵**：brief 每条需求行 → 覆盖它的工单（编号），找出**零覆盖行**与覆盖理由存疑的行；
- **边检查**：blocking 边有无**环**、**断链**（工单隐含依赖别的工单却没声明）、**漏边**（声明的依赖少了前置）。

盲评者不得引入 brief 之外的新需求。

**快速模式**（仅当用户明说要快 / 要省）：2 个盲评者（票数 `2/2`、`1/2`）。

### 4. 裁决与合入（主代理）

- 共识（≥2/3 盲评者指出，含 `3/3`）→ 免检采信；孤证（`1/3`）→ 对照 brief 逐条核对，成立才合入；
- 成立的缺失 → 补工单或并入既有工单；成立的边问题 → 补边 / 重排 blocked_by；
- 拿不准的需求行不硬判：列入问题清单随 quiz 一起交用户拍板。

### 5. 呈现与发布

照上游 quiz 用户的格式呈现工单清单，**末尾附覆盖矩阵**（需求行 × 工单编号）；确认后照上游发布（tracker 原生 blocking 边或本地文本）。

## 完成判据

- 覆盖矩阵无零覆盖行（零覆盖的要么补上、要么标「用户确认砍掉」）。
- blocking 边无环、无断链、无漏边（裁决后）。
- 每条盲评意见有裁决记录（合入 / 剔除 + 依据）。

## 降级与边界

- 某盲评者失败 → 同模型重试一次；再失败按剩余人数出稿：2 个仍算对拍（标注），仅 1 个标注「未经盲评对拍」。
- 覆盖矩阵以 brief 的需求行为准；brief 本身漏了的对话需求，靠起草前的物化步骤兜底，盲评不负责补 brief。
- 3 个是默认；快速模式 2 个并标注；4 个及以上不外推。
