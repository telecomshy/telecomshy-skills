# shy-to-spec

`to-spec` 的强化封装。**上游技能是流程事实源**：先用 Skill 工具加载 `to-spec`（失败则读 `~/.agents/skills/to-spec/SKILL.md`），按它执行（探索仓库、seam 确认、模板、发布到 issue tracker），仅在「写规格」与「发布」之间插入下面的盲评环。

分工依据：子代理看不见对话，**起草不外包**；独立眼睛的价值由盲评拿回来。盲评者数取 3（三档票数 `3/3`、`2/3`、`1/3`，与对拍同一甜点）；并行发出，3 个与 2 个延迟几乎相同。

## 覆盖点

### 1. 物化 brief（起草前）

把对话里的原料落到一个临时文件（Temp 目录），供盲评者读：

- **用户原话引述**（逐字，含被否定掉的说法）；
- **已定决策**（谁拍的板、定了什么）；
- **已知约束**（技术 / 平台 / 范围）；
- **未决问题**（对话里悬着的）。

**只收原料，不下结论**：brief 里出现结论会把起草者的理解发给所有盲评者，对拍就失效了。

### 2. 起草（主代理）

照上游模板起草规格。上下文只在主代理手里，这一步就是它写。

### 3. 盲评（3 个子代理）

并行、互不可见，输入 = brief + 草稿原文，模型 = **三个不同模型各一**（ID 查找顺序：仓库 `docs/agents/subagent-models.md` → 用户级 `~/.config/opencode/shy-models.md` → 问用户；某模型不可用则凑满 3 个：一模型 2 个 + 另一模型 1 个）。解析模型 ID 先查模型目录，看不到想要的加 `all: true`；不猜 ID。任务只有一个——对照 brief 挑草稿的漏，每条给位置 + 引语：

- **缺失**：brief / 引语里有、草稿没有的需求；
- **加戏**：草稿有、brief 里找不到依据的内容；
- **矛盾**：草稿内部或与引语相抵触之处。

盲评者不得引入 brief 之外的新事实。

**快速模式**（仅当用户明说要快 / 要省）：2 个盲评者（票数 `2/2`、`1/2`）。

### 4. 裁决与合入（主代理）

- 共识（≥2/3 盲评者指出，含 `3/3`）→ 免检采信，合入草稿；
- 孤证（`1/3`）→ 逐条对照 brief 与对话原文核对，成立才合入，剔除的记一句依据；
- **分歧点 = 对话歧义**：两个及以上盲评者对同一处理解不同、或裁决拿不准的，不硬判——整理成一份问题清单问用户（可用 `to-questionnaire`），澄清后合入。

### 5. 发布

照上游：写规格、发布到 issue tracker、打 `ready-for-agent`。发布前把裁决结果过一遍（完成判据）。

## 完成判据

- 每条盲评意见有裁决记录（合入 / 剔除 + 依据）。
- 分歧问题已向用户澄清并合入，或用户明示跳过。
- brief 留档（临时文件路径写进迭代说明，或附进发布内容），结论可回溯到引语。

## 降级与边界

- 某盲评者失败 → 同模型重试一次；再失败按剩余人数出稿：2 个仍算对拍（标注），仅 1 个标注「未经盲评对拍」。
- 裁决拿不准的走分歧问题清单，不硬判、不静默删。
- 3 个是默认；快速模式 2 个并标注；4 个及以上不外推。
