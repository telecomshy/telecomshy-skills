# 工单 / 契约分离与复审收敛 · 设计说明

> 状态：**冻结（v-final）**。面向：`shy-skill-suite` 的维护者与使用者。
> 缘起：2026-09-18 与用户的讨论——「每次复审都发现问题、修完又有」「功能需求与修复需求混在 REQ 里分不清」。
> **冻结规则（可执行）**：**无真实使用触发（真实失败 / 用户显式要求）不得改本设计文档**——否则每次评审都会以"某机制还没接线"为由开新版，重演它自己诊断的循环（§10.3）。剩余项进 `cleanup.md` / REQ 当 backlog，不进新一轮设计。
> 修订史见文末。

---

## 1. 问题

### 症状 A：复审不收敛

历轮复审候选数：iteration-1 = 54、iteration-2 = 70、iteration-3 = 20（**非单调**）。修完一轮，下一轮又出新项；旧 REQ 的验收标准反复被检出"与实现不一致"，于是反复**修改 REQ 文档**。

### 症状 B：功能与修复混在一起

49 份 REQ 里约 23 份是 fix / 硬化 / 去重 / 流程类。用户想看"这技能能做什么 / 下一步做什么"，列表一半是内部修补，且分不清"谁提的、为什么提"。

### 根因：一个 `REQ-NNNN` 同时干四件事

| 承载 | 本质 | 变化频率 | 该被每轮复审吗 |
| --- | --- | --- | --- |
| 该技能**该做什么**（契约） | 持久 | 很低 | 该（对象应是"当前契约"，不是历史） |
| 一次**改动工单** | 瞬时 | 一次性 | **不该**（closed 即历史） |
| **验收 / 证据** | 判定依据 | 一次性 | 不该 |
| **迭代记录** | 账本 | 只增 | 不该 |

于是：契约变了 → 改历史文件正文 → 复审重扫历史 → 又发现"契约对不上" → 再改 REQ。**循环。** 且修复本身是**加法**，加法制造新的重复 / 漂移（`REQ-0032` 自述：8 条里 5 条是上一轮新引入的）。

---

## 2. 核心判断

断层不在「功能 vs 修复」，而在两组被混同的东西：

1. **持久契约 vs 瞬时工单** —— 前者该每轮查、后者该冻结。
2. **确定性回归（Gate） vs 对抗式发现（Discovery）** —— 前者每次跑、后者低频；病在把 Discovery 的输出当 Gate 的失败。

「功能 / 修复」只是**工单上的标签**。

---

## 3. 目标模型

| 层 | 内容 | 形态 | 每轮复审 |
| --- | --- | --- | --- |
| **契约** | 技能当前行为 | 技能文件 + **不变量集**（见 §4.2 准入） | 每轮跑不变量 |
| **工单** | 一次改动（feature / fix / …） | `REQ-NNNN` + `kind`/`source`/`epic`；落地即冻结 | **从不重扫** |
| **问题台账** | 未解决 / 已解决的问题 | `cleanup.md`（自洽项）+ fix 工单 | 只读计数 |
| **状态** | 跨轮持久事实 | `state.json`（converged / 迁移债 / 预算） | 读 |
| **发现** | 复审原始项 | findings（每轮快照） | 分拣后消失 |
| **账本** | 改了什么、何时 | git（+ 工单迭代记录） | — |

要点：契约的单一事实源就是**技能文件本身**，不另建平行散文；**REQ 全部冻结**；用户功能需求照常落 REQ（`kind: feature, source: user`），落地后冻结为历史。

## 4. 机制

### 4.1 工单字段

```yaml
kind: feature | fix | refactor | docs | hygiene   # 工单性质（展示/筛选用）
source: user | review | retro                      # 谁提的
epic: FEAT-NNNN                                     # 可选：把拆成多份增量的一个功能归组
```

`kind` / `source` / `epic` **只影响展示与读数**，不影响复审范围。

### 4.2 验收标准三态分类（落地时判定）

每条验收标准在**工单关闭那一刻**归入三态，只有第一态进不变量集：

| 态 | 判据 | 去向 |
| --- | --- | --- |
| **不变量** | "以后**每次**都要成立"的行为 / 接口 | 写成 `check:` 或行为 eval |
| **episode** | "这次改动的一次性事实"（旧值、实测数字、某份文档被改、某 REQ 被取代） | 留在工单里，**冻结、永不重扫** |
| **未定** | 判不准 | **迁移债**：计数、必须趋零（见 §4.7），**不默认任何一方** |

**不变量的准入（严格）**——两条硬规则：

1. **只收行为 / 接口**：脚本 I/O、退出码、触发率、以及**技能自身运行产物的计数**（脚本数、命令数、notes 条数、输出记录数）。
2. **不得依赖散文文档的措辞或结构**：判据是——**"把这段文档改写 / 合并章节，它会变红吗？"** 会 → 不是不变量（如"`lifecycle.md` 含『实现路』"、"`subagents.md` 含 5 个角色"、"`writing-skills.md` 含 10 组 lever"）→ 归**问题台账**或 episode。

**为什么三态而不是二态**：二态必须给"判不准"一个默认值。默认"不变量"→ 噪声永久污染 Gate；默认 episode → 真回归静默漏检。**两者都是净风险，所以不设默认**——判不准就挂"未定"，可见、计债、趋零。

**分类是拆句，不是贴标签**：一条标准常同时含两态。例——`description ≤ 1024 字符（实测 166；REQ-0021 后由 150 增至 166）` 拆成：不变量"≤ 1024 字符" + episode"实测 166 / 150→166"。

### 4.3 问题台账（持久、可关闭、跨轮可对账）

**自洽 / 卫生类** → `docs/<skill>/cleanup.md`，每条：

```yaml
id: CL-0001              # 稳定 id（跨轮不变）
dedup_key: <归一化指纹>   # 去重键：同一问题再次发现时命中已有条目，不重复登记
first_seen: iteration-N
status: open | fixed | wontfix
resolved_in: iteration-M | <commit>   # 关闭时填
evidence: <命令 / 输出>
```

- **修复类** → `kind: fix` 工单，**仅限"改变行为"的修复**（它才产出不变量）。四档：`open` = `draft`/`ready`/`in-progress`（被 `blocked` 的另标"不可动"）；`fixed` = `done` **且其不变量当前为绿**；`延后` = `deferred`；`不做` = `out-of-scope`/`superseded`。
- **纯卫生修复**（订正数字、删重复，不产出不变量）**不是 fix 工单**，直接进 `cleanup.md`——所以"fixed 依赖不变量为绿"只对行为修复适用，不产生"无不变量的 fix 永远算不了 fixed"。
- **读数 B 的三个来源**：`cleanup.md` 条目 + fix 工单 + **当前为红的不变量**（一个 feature 的不变量红了，本身就是一条 open 问题，不属于任何工单，B 直接收它）。
- **关闭路径（否则 open 只增不减）**：每条 `open` 须在 **N 次 Gate 运行内**转 `fixed`/`wontfix`（Gate 每次改动都跑，是**确定性的时钟**；不用"Discovery 轮"——那没有时钟）。
- **`wontfix` 需用户显式决定**（记谁、何时），agent 不能自行改判——否则收敛可被"批量 wontfix"游戏化。
- **分类时点**：分类是**关闭工单**的一部分（实现路、评审路回写都做），由**关闭者**执行；判不准的挂"未定"，**不阻塞关闭**，进迁移债。
- **对账规则**：`done` 只表示"关闭那一刻成立"。若某 fix 的不变量之后转红 → **该问题重开**（B 加一条 open），B 以**不变量的当前颜色**为准，不以 `done` 为准。

### 4.4 持久状态 `docs/<skill>/state.json`

**只存"推不出来的事实"**（与 `track_requirements.py:19`「frontier 由状态推导、不落盘索引文件」一致）——派生量一律现算，不落盘，避免第二事实源漂移：

```json
{"converged": false, "converged_since": null,
 "invariant_budget_growth": 2, "cleanup_ttl_gate_runs": 3,
 "debt_targets": {"unclassified_criteria": 0, "unmigrated_reqs": 0}}
```

- **不存** `open_issues` / `invariant_count` / `migration_debt` / `unmigrated_reqs`——这些由工具每次现算。
- **写权**：`state.json` 只由**专门的写命令**改（`track_requirements.py --write-state`，评审 Step 8 由主 agent 调用）；**Gate（`run_checks.py`）只读**，保持幂等与只读性。

### 4.5 两个读数（用户要的"功能 / 问题"分离）

- **读数 A ·「功能实现了吗」**：`track_requirements.py --kind feature` 按 `epic` 分组、按状态展示实现度。**归属规则：不变量的红不属于 A**——A 只说"功能是否落地（工单状态）"，并给出指针"其 N 条不变量当前有 M 条红 → 见读数 B"。
- **读数 B ·「有多少问题、修了几个」**：`cleanup.md` + fix 工单合并计数，四档（open / fixed / 延后 / 不做）。**不变量的红归这里**（它是"当前问题"，不是"功能没实现"）。
- **同一 fix 工单在 A / B 的显示**：A 显示其 `done`（已落地），B 显示其不变量当前是否绿；若工单 `done` 但不变量红，A 侧标注"已重开 → 见 B"，**给同一张票一个连贯解释**，不让用户看到两个相反状态。
- **一句话对账**：**A 看工单生命周期，B 看问题当前状态；不变量的颜色只进 B。** 两个读数不共享同一份数，因此不会互相污染。

### 4.6 Gate vs Discovery

| | Gate（确定性） | Discovery（对抗式） |
| --- | --- | --- |
| 何时 | **每次改动** | **(a) 真实失败（任务做砸 / 真 bug）；(c) 用户显式要求** |
| 内容 | 不变量集 + 行为 eval + selftest + **迁移债计数 + 不变量预算** | 完整三轴 + 启发式找新问题 |
| 产物 | 绿 / 红 | findings（**提案**，非"必改回归"） |
| 收敛 | 按构造收敛 | 不要求收敛 |

**Discovery 触发点只有 (a)(c)。** 不再有"按计划重扫"，也**不设"触及行为就 Discovery"**——"是否触及行为"在落地时无法机械判定（§1 已证：验收标准与实现无登记对应，判它只能靠声明或再跑一遍，都是循环）。改动一律只跑 **Gate**。

**部署 / 自包含（AGENTS.md 硬约束）**：`state.json` / `cleanup.md` 在 `docs/<skill>/`，**不随技能分发**。技能单独部署时 Gate 找不到 `docs/` → **明确报 `n/a（非开发仓库）`**，不静默当 0（否则会错误收敛）。Gate 在无 `docs/` 时不得判绿。

### 4.7 停止规则、迁移债门、不变量预算、契约漂移防护

- **停止规则**：每轮 Discovery 在 Step 8 由主 agent 算 verdict；**0 个 P0/P1 且迁移债达标** → 用 `track --write-state` 把 `converged: true` 写进 `state.json`（持久），不排下一轮。只有 (a)(c) 才重开。
- **迁移债（两个单位，分开计数，不相加）**：`unclassified_criteria`（未分类标准数）+ `unmigrated_reqs`（未迁移 closed REQ 数）；各自 target 落 `state.json`，**不相加成一个整数**。
- **债务门（V3 统一口径）**：`debt_targets` 的目标就是 **0**（债归零 = A 的消失点，可验收）；迁移期的**过程规则**是**单调不增 + 新写 / 改写的 REQ 关闭时当场分类**（不再新增债）。即"**目标清零，路径允许逐步**"，与 `state.json` 的 `{0,0}` 对齐。Gate 带债时 `exit≠0`（已接线）。
- **债务门（收窄，堵住"带病收敛"）**：`converged` 要求 —— ① 两个债各自达标（target 落 `state.json`）；② **没有任何"已知不可靠的 check"仍在跑**。即：未定项要么分类，要么**显式豁免并计数**（`wontfix`），**不能挂着"未定"就判收敛**。
- **迁移期的覆盖（修正"未定项仍跑旧子串 check"的自伤）**：未定项在迁移期仍跑旧子串 check，但被标 `migration`、**不计入 P0/P1 verdict**（已知噪声不能既当噪声又当回归信号），同时**阻止 `converged`**（见上）。这样"先保覆盖"不牺牲"收敛可信"。
- **不变量预算**：`invariant_budget_growth` 是**增长率上限**（每个 feature 落地净增 ≤ k），不是固定条数（现 61 条离任何大数都远，固定数无压力）。超限 → Gate 红，须先合并 / 退休。
- **契约漂移防护**：不变量集**版本化**——**改一条不变量必须挂工单**（像 schema 变更）。Gate 比对"当前不变量集"与"上次提交的快照"，发现**未挂工单的改动**即报红。堵住"`REQ↔实现`漂移"变成"`不变量↔实现`漂移"。

## 7. 权衡与放弃

- **放弃**"需求是活文档"的旧含义：契约（技能文件 + 不变量）是活的；工单是历史。不能再"读一份 REQ 就知道技能现在是什么样"。
- **放弃**"每轮全量重扫历史"的安心感，换来收敛。
- **接受"未定"三态**：多一个状态，换来"不被迫选错默认"。
- **`converged` 不等于"没新问题"**：只等于"没有**自己制造**的循环"。真实失败永远会有。
- **能力可无界**：不变量预算是对耦合成本的**人为上限**，不是自然定律。

## 9. 验证现状与缺口（诚实标注）

> 本节与 §10 是**证据 / 台账**，不是提案。按 §1 的根因（一个文件干多件事），它们本应进 REQ / `cleanup.md`（见 `cleanup.md` `CL-0018`），暂留此处待搬迁。

**已验证（旧问题）**：子串 `check:` 会在无害措辞改动上假警报。实验可复现：`docs/shy-skill-suite/design/pilot-0046.py`（隔离副本、不动仓库，退出码 0）——仓库已迁移，该脚本现为**回归守卫**（`trial-run-0046.py` 已退休：其"假警报存在"的断言前提被 `REQ-0050` 消灭）。

**已验证（方案的一个关键点，单 REQ 试点）**：在同一实验中，**行为不变量**（`req0046-unimplemented-skipped`）不受措辞改动影响、且能抓到注入的真回归——即"行为不变量比子串 check 假警报率低"。
