# REQ-0001 拆工单前加覆盖矩阵与依赖边盲评（3 个盲评者），堵漏拆和断链，不改上游 to-tickets

## 问题与目标

`/to-tickets` 的工单拆分漏掉需求、或 blocking 边断链/成环，都是静默失败（拆完看着像全的）。这两个角度**机械可验**，正适合盲评。目标：主代理起草 + 3 个盲评子代理做「需求覆盖矩阵」与「依赖边检查」+ 主代理裁决合入（三档票数 3/3、2/3、1/3），清单附矩阵交用户 quiz。触发场景：用户要「shy 拆工单」、担心漏拆 / 依赖边有误。

## 触发与分支

「/shy-to-tickets」「shy 拆工单」→ 加载上游 `to-tickets` 执行（gather context、探索、vertical slice、wide refactor、quiz、发布），在「草拟切片」与「quiz 用户」之间插入盲评环。

## 行为与步骤

1. **物化 brief**（临时文件）：被拆需求逐行编号 + 原话引述（spec 原文需求行或对话决定）。
2. **草拟**：主代理照上游规则出工单（标题 / 交付行为 / blocked by 边）。
3. **盲评**（3 个子代理并行、互不可见、模型尽量不同）：各出两份检查——
   - 覆盖矩阵：brief 每行 → 覆盖工单编号，标出零覆盖行与存疑行；
   - 边检查：环、断链（隐含依赖未声明）、漏边（声明少前置）。
   不引入 brief 之外新需求。
4. **裁决合入**：共识（≥2/3）免检、孤证（1/3）逐条核对；缺失 → 补工单或并入；边问题 → 补边 / 重排；拿不准的行列入问题清单随 quiz 交用户。
5. **呈现发布**：照上游 quiz 格式 + 末尾覆盖矩阵（需求行 × 工单编号），确认后照上游发布。
6. **快速模式**（用户明说要快）：2 个盲评者（票数 2/2、1/2）；降级同理按剩余人数出稿并标注。

## 脚本与资源

- 技能文件：`~/.agents/skills/shy-to-tickets/SKILL.md`（薄封装，无 scripts/references）。
- brief 落 OS 临时目录，路径在交付说明中可追溯。

## 降级与边界

- 某盲评者失败 → 同模型重试一次；再失败按剩余人数出稿：2 个仍算对拍（标注），仅 1 个标注「未经盲评对拍」。
- 矩阵以 brief 需求行为准；brief 自身漏行不在盲评职责内，靠物化步骤兜底。
- 3 个是默认（与对拍同一甜点：三档票数）；快速模式 2 个并标注；4 个及以上不外推。
